Randomised demo route generation

Review of current state, and a plan for an authentic local-first simulation.

The generator has no concept of terrain, and that is by design and under test. Contacts are placed at uniformly random world coordinates, roughly 92% of them have no destination at all, and per-category behaviour amounts to two tuning constants. A car and a fighter jet trace the same shape at different speeds.

The fix needs no new third-party services. You already host a full-planet OpenMapTiles vector dataset locally (data/tiles/openmaptiles.mbtiles, 95 GB, z0–14), served by the existing tiles service. It contains roads, water, runways and aerodromes — everything the three vehicle classes need.

Review of current state

as built

Nine findings, ordered by impact on authenticity. Each cites the code it comes from.

Critical Placement ignores terrain — and a test enforces it

randomWorldOrigin samples uniformly across ±85° latitude and ±180° longitude. Since roughly 71% of Earth is ocean, most cars and trucks spawn mid-Atlantic and most boats spawn inland. Antarctic and open-ocean spawns are common.

// apps/web/src/lib/demo-scenario.ts:149
function randomWorldOrigin(random: () => number): DemoOrigin {
  return {
    latitude: (random() - 0.5) * 2 * DEMO_MAX_ABS_LATITUDE,
    longitude: (random() - 0.5) * 360,
  };
}

Critically, this is not an oversight. demo-scenario.test.ts L165–196 asserts latitude span > 20°, longitude span > 40°, and fewer than three close pairs. The global scatter that causes the implausibility is an enshrined contract and must be deliberately replaced.

Critical About 92% of contacts have no destination

GROUP_JOIN_PROBABILITY = 0.08, and endPoint is only populated when plan.sharedPath is true, which requires a multi-member travel group. Every solo target therefore takes the generateWanderEvents path: an endless heading random-walk with no intent, no origin meaning, and no arrival.

// apps/web/src/lib/demo-scenario.ts:444
const endPoint: PositionPayload | undefined = plan.sharedPath
  ? { /* … A→B corridor … */ }
  : undefined;   // solo targets just drift

The rare group that does get an endPoint receives a noisy great circle from generatePointToPointEvents — better, but still geographically arbitrary.

Critical Per-category behaviour is two tuning constants

The only differentiation between a truck and a fighter jet is a speed range and a per-step heading/speed limiter. The path geometry generation is identical.

// apps/web/src/lib/event-generator.ts:22
const CATEGORY_MOVEMENT_SMOOTHING: Record<VehicleCategory, MovementSmoothing> = {
  aircraft: { maxHeadingChange: 4,  maxSpeedChangeFraction: 0.06 },
  boat:     { maxHeadingChange: 7,  maxSpeedChangeFraction: 0.08 },
  car:      { maxHeadingChange: 14, maxSpeedChangeFraction: 0.16 },
  truck:    { maxHeadingChange: 12, maxSpeedChangeFraction: 0.12 },
};

Critical Aircraft have an altitude number, not a vertical profile

demoAircraftAltitude picks one band once at spawn. lerpAltitude linearly interpolates start to end. And for groups, endPoint.altitude is set equal to startPoint.altitude, so cruise altitude never changes. Solo aircraft reuse startPoint.altitude for every wander point.

There is no climb, no descent, no loiter, and no return-to-origin anywhere in the system.

High Speed bands are too wide and detached from the declared subtype

CATEGORY_SPEED_RANGES.aircraft is 90–1400 kt, sampled uniformly. Meanwhile vehicleSubtype is chosen independently at L460. The result is that a “Transport” can cruise at 1,300 kt and a “Multi-role fighter” can plod at 95 kt. car: 10–85 kt is up to 98 mph on a random walk.

High The only spatial constraint is a rendering guard

DEMO_MAX_ABS_LATITUDE = 85 with steerHeadingForLatitudeBound exists purely to avoid Web Mercator clip-line artifacts near the poles. It is a render concern being mistaken for a realism feature. There is no land/water test, no road network, and no airport awareness in the entire generator.

High Sampling is too coarse and uniform in time to represent turns

pointCount = 10 + floor(random() * 15) yields 10–24 points per track, and distributeTimestamps spaces them evenly in time. A road route needs its vertices concentrated at corners. At this density, road-following is not expressible.

Medium Latent performance wall in the playback engine

positionEventsForTarget calls sortEvents(scenario.events) inside a per-target loop, making interpolated preview O(targets × n log n). At 100 targets × 150 points that is a 15,000-element sort performed 100 times per preview frame. Fine at today's ~2,400 events; a wall at higher fidelity.

// apps/web/src/lib/simulation-engine.ts:161
function positionEventsForTarget(scenario: SimulationScenario, targetId: string) {
  return sortEvents(scenario.events)  // re-sorts the whole list, per target
    .filter((event) => event.targetId === targetId && event.position);
}

Separately, runtime state persists to localStorage through safeWrite, which swallows quota errors silently — so a large scenario can fail to persist with no signal.

Keep Two things are already right and worth building on

Kinematic consistency. Distance is derived as speed × elapsed time, assertFeasibleEndWindow rejects windows that would require exceeding category maximums, and position.speed is always authored so runtime never invents speeds. The new routers should honour exactly this contract.

Non-uniform spacing is already safe. interpolatePositionSnapshot computes progress per segment, so dense-at-corners, sparse-on-straights waypoints need no engine change. This is what makes the adaptive densification budget viable.

The asset you already have

zero new services

A full-planet vector dataset is already downloaded, already served, and completely unused outside basemap rendering.

data/tiles/openmaptiles.mbtiles is an OpenFreeMap / planetiler planet build: 95 GB, zoom 0–14, schema version 3.16.0, OSM data dated 2026-06-15. It is already mounted into the tiles service in docker-compose.yml. Every layer the three vehicle classes need is present.

LayerZoomsUseful fieldsUsed for
transportation4–14 class, oneway, surface, toll, expressway, ramp, brunnel, access Road graph for cars and trucks. Also carries class=ferry — real maritime routes.
water0–14 class (ocean, lake, river, dock), intermittent Navigability mask for boats; land/water test for placement.
waterway3–14 class (river, canal), name Inland vessel routes.
aeroway10–14 class (runway, taxiway, apron), ref Runway geometry, so departures and approaches align to a real runway heading.
aerodrome_label8–14 icao, iata, name, class, ele_ft Origin and destination airport selection.

Zoom availability gives a routing hierarchy for free

OpenMapTiles introduces road classes progressively by zoom, which is exactly the structure a hierarchical router wants. Motorways appear from z4, trunk and primary around z7–8, secondary around z9–10, minor roads from z12. A long-haul truck corridor can therefore be planned from a handful of z10 tiles (each covering roughly 40 km) and only refined at z13–14 near the endpoints. This keeps tile fetch counts low without sacrificing realism.

Dev and Docker read byte-identical geography

Rather than hardcoding a tile URL template, resolve it from a TileJSON endpoint. This mirrors the existing VITE_MAP_STYLE_* pattern in packages/env/src/web.ts and .env.example, and it is version-proof.

EnvironmentVITE_GEO_TILEJSON_URLResolves to
Dev (Vite)https://tiles.openfreemap.org/planet…/planet/20260621_080001_pt/{z}/{x}/{y}.pbf
Dockerhttp://tiles.adversary/data/openmaptiles.json…/data/openmaptiles/{z}/{x}/{y}.pbf

Verified: the public OpenFreeMap TileJSON resolves to build 20260621_080001_pt, and data/tiles/SOURCE.txt records the local mbtiles as …/planet/20260621_080001_pt/tiles.mbtiles. Both report schema version 3.16.0. Dev and production read the same data, so the split carries no divergence risk.

Region model

correctness

The current presets would reproduce the exact bug being fixed. This is the one place where a naive implementation quietly fails.

Trap Today's presets are 9 out of 10 maritime

DEMO_START_LOCATIONS contains English Channel, North Sea, New York Harbor, Singapore Strait, Tokyo Bay, Persian Gulf, South China Sea, Mediterranean and Gulf of Aden — all water. Only London is land. Wiring those into a region picker and then asking for trucks puts road vehicles in open ocean, which is precisely the failure this work exists to remove.

Replace the flat preset list with a typed catalogue:

interface DemoRegion {
  id: string;
  name: string;
  bbox: [west: number, south: number, east: number, north: number];
  /** Categories this region can authentically host. */
  supports: readonly VehicleCategory[];
}
  • A selected region only receives compatible contacts. An incompatible contact relocates to another selected region that supports its category.
  • If no selected region supports a category, those contacts fall back to "anywhere" validity-filtered sampling, and the completion toast says so.
  • supports is derived from real geometry by the phase 1 build script — each bbox is probed for usable road classes, navigable water and nearby aerodromes — rather than hand-asserted. A region cannot claim to host trucks unless the tiles actually contain roads there.
  • The catalogue gains land and mixed-coastal entries (Central Europe, US Eastern Seaboard, Benelux) alongside the existing maritime straits.
  • The origin pin stays and wins. demoOrigin and MapLocationPicker remain a separate override, giving one unambiguous precedence rule: pin > regions > anywhere.
  • other category is routed by terrain rather than declaration: sea router if its start point classifies as water, road router otherwise. Documented assumption, easy to override.

Generation budget and streaming

under ~2s to first contact

Targets are revealed as their routes complete, rather than blocking on all 100.

  • scenario-planner.ts exposes an async iterator or onTargetReady callback instead of resolving one finished scenario, so the builder can append targets progressively.
  • Bounded worker concurrency, starting around 4–6 in-flight route requests, to avoid a fetch stampede against the tile source.
  • Cancellation via AbortSignal, threaded from a Cancel button in the dialog through the planner into the worker, aborting in-flight tile fetches too.
  • Progress feedback showing routed count against total.
  • Aircraft are planned first, because they need no runtime tile fetches at all — airports and runway headings come from the seed bundle. First contacts therefore appear almost immediately while road and sea routes are still resolving.

Watch Streaming interacts with existing selection state

loadRandomDemo currently calls setSelectedTargetId(demo.targets[0]?.id) and setDraft(...) after generation completes. With targets streaming in, these must fire once on the first ready target, not on every append, or the builder's selection will thrash as contacts arrive.

Target architecture

pipeline

All tile decoding and routing runs in a worker. Every stage can degrade to the existing synthetic generator.

Per-class routing strategy

RequirementData sourceMethod
Cars and trucks follow roadways transportation LineStrings Stitch tile-clipped lines into a graph by quantizing node coordinates to about 5 decimals (~1.1 m), which rejoins geometry split at tile boundaries. Weight edges by length divided by class speed; respect oneway and access; exclude rail, path, track, aerialway, transit. Plan the long-haul skeleton at z10 and refine locally at z13–14. Trucks bias to motorway, trunk and primary; cars may use minor and service roads.
Boats stay in waterways and oceans water polygons, waterway lines, transportation class=ferry Prefer real ferry LineStrings where they exist — these are genuine maritime routes. Otherwise A* over a navigable grid rasterized from class=ocean and class=lake polygons at z6–8 with 8-neighbour connectivity, which keeps vessels off land and yields plausible lanes. Snap starts near harbours and ferry terminals from the seed bundle.
Planes fly common patterns, loiter, and can return to origin aerodrome_label + aeroway class=runway Pick an origin and destination aerodrome, then compose a profile: runway-aligned departure, climb at the profile's rate, cruise great circle at a flight level suited to distance and subtype, optional loiter (racetrack or orbit), descent, runway-aligned approach, landing. Return-to-origin is simply destination equals origin with a loiter or patrol block in the middle. Because airports and runway headings are precomputed into the seed bundle, the common aircraft case needs no runtime tile fetch at all.

Implementation phases

1 gate + 6 phases

A gating spike comes first. After that, each phase leaves the app working. Phase 0 and 1 are prerequisites; the three routers in phase 2 are independent of each other.

GO

Viability spike — resolved, road routing is viable

The riskiest assumption in this plan held. Tile-clipped transportation geometry does stitch back into a connected graph, so runtime client-side routing goes ahead and the offline corridor-mining fallback is not needed. Measured on real London tiles (z14 2×2 block 14/8185/5447–14/8186/5448, plus the same area at z10) and independently re-verified, including confirming the sample A* route genuinely crosses a tile seam.

LayerNodesEdgesComponentsLargest component
z14 all classes32,27031,9911,98467.56%
z14 drivable8,7248,59959571.26%
z14 arterial5,9386,17717988.18%
z10 arterial20,52721,70083179.84%

Seam stitching at z14 arterial: 54, 48, 31 and 27 shared nodes across the four adjacent tile pairs, and the largest component spans all four tiles.

Parameters now locked for phase 2a

  • Quantize to 5 decimal places (~1.1 m), with no snap tolerance. The snap sweep says snapping is not worth its complexity: at 0.5 m, 1 m and 2 m the component count stays exactly 179 while the largest component slightly shrinks. Only 5–10 m moves it at all, and that is also where false bridge-to-ground merges begin.
  • Class filtering is the real connectivity lever, not snapping. Filtering to arterial lifts the largest component from 67.56% to 88.18% and collapses components from 1,984 to 179 — and 177 of those 179 are tiny stubs of 20 nodes or fewer.
  • Snap endpoints into the largest component, not merely to the nearest edge. About 12% of arterial nodes sit outside it, so nearest-edge snapping would occasionally strand a vehicle on an isolated stub.
  • Fetch by corridor, never by bbox. A 10 km corridor at z14 is ~21 tiles; a 25 km bbox is 289.
  • No class filter needed at z10 — the z10 drivable and arterial graphs came out byte-identical, because OpenMapTiles already carries only arterial classes at that zoom.

Carry forward The long-haul layer is the weaker one

The z10 skeleton is more fragmented than z14 arterial — 79.84% largest across 831 components, versus 88.18% across 179. Boundary effects inflate this, since the z10 block spans roughly 48 km and many roads simply continue outside the sample. Still, phase 2a should expect long-haul planning to depend on endpoint snapping more than local refinement does, and should degrade that single track rather than fail hard.

1

Seed bundle and terrain classification

The seed bundle is what makes region selection instant, aircraft routing fetch-free, and offline operation possible.

  • new scripts/build-geo-seeds.mjs — reads data/tiles/openmaptiles.mbtiles directly using Node 22's built-in node:sqlite (verified available on v22.14), so no new dependency. Emits apps/web/public/geo-seeds.json containing aerodromes (icao, iata, name, class, ele_ft) with runway headings derived from aeroway class=runway bearings, ports and ferry terminals, coarse sea-lane waypoints, per-region road anchors, and the region catalogue itself. Filter aerodromes to those with an IATA code or a runway over roughly 1,500 m to keep the file to a few thousand entries.
  • new apps/web/src/lib/geo/terrain.ts — classifyPoint(lngLat) returning water class via point-in-polygon over water at z8–10, plus the nearest road candidate. This is the primitive that makes globally-valid rejection sampling work: sample a candidate, probe, accept or retry within a bounded attempt count, then relocate.

The bundle is precached automatically by the existing workbox glob **/*.{js,css,html,ico,png,svg,woff2,mjs,json}, so it doubles as the offline tier with no config change.

The three routers

Independent of one another, so they can be built and reviewed separately. Each returns a plain polyline; none of them knows about events or timing.

  • new apps/web/src/lib/geo/road-router.ts — hierarchical A* over a stitched road graph, with class-weighted edges and per-category class preferences.
  • new apps/web/src/lib/geo/sea-router.ts — ferry-line preference with water-grid A* fallback.
  • new apps/web/src/lib/geo/air-router.ts — aerodrome pairing, runway-aligned departure and approach, climb/cruise/descent, loiter patterns, and return-to-base.
3

Kinematics and track synthesis

This is where the speed realism finding gets fixed, and where the point budget is enforced.

  • new apps/web/src/lib/geo/vehicle-profiles.ts — the single source of kinematic truth, keyed by vehicleSubtype rather than category, which directly fixes the “Transport at 1,300 kt” problem. Today VEHICLE_SUBTYPES is only a flat list of display strings with no physics attached; every entry gains a full profile carrying cruise band, max speed, climb and descent rate, turn radius, typical flight level, and loiter / return-to-base flags. CATEGORY_SPEED_RANGES is demoted to a fallback for targets with no subtype, and CATEGORY_TOP_SPEED_KNOTS remains the hard clamp used by clampSpeedToCategory. Turn radius and climb rate feed the synthesis step below; the loiter and RTB flags drive the air router's pattern choice back in phase 2.
  • new apps/web/src/lib/geo/path-to-events.ts — walk the routed polyline at profile speed, apply turn-rate limits and speed reduction through turns, then simplify with Douglas–Peucker by perpendicular distance in metres to hit the 60–150 point budget. Emit authored speed and altitude per point, since the engine already prefers authored speed.

Reuse the assertFeasibleEndWindow semantics so a routed distance that cannot fit the authored window is retimed or rejected, rather than producing a physically impossible track.

Risks and mitigations

known unknowns

The honest list. Road routing from vector tiles is the riskiest piece.

RiskWhy it mattersMitigation
Graph stitching across tile boundaries Vector tiles clip geometry per tile, splitting LineStrings. If nodes do not rejoin, the router finds no path. Resolved — the spike returned GO. 5dp quantization yields an 88.18% largest component across a real z14 seam, with 27–54 stitches per adjacent tile pair. Class filtering, not snap tolerance, turned out to be the lever. The offline corridor-mining fallback is no longer needed.
Tile fetch volume A dense urban z14 tile can hold thousands of features; covering a long route naively could mean hundreds of fetches. Hierarchical routing: z10 skeleton for long haul, z13–14 only near endpoints. LRU cache in the worker. Aircraft avoid runtime fetches entirely via the seed bundle.
Tile-simplified geometry at low zoom Planetiler simplifies per zoom, so a z10 motorway is coarser than the OSM way. Acceptable for the skeleton, since the visual result is a smooth motorway corridor. Refine near endpoints where the viewer is likely to zoom in.
Async generation breaks existing tests Every createDemoScenario test is synchronous, and the docs example calls it during render. Phase 0 decouples the docs example first. Keeping createSyntheticDemoScenario synchronous preserves fast tests.
Rejection sampling could loop “Anywhere” mode probing for a road-valid point could retry many times over ocean. Bounded attempt count, then relocate to a seed-bundle anchor, then degrade. Bias initial candidates toward landuse and place presence rather than pure uniform sampling.
Review doc ships in the build This file lives in apps/web/public/, so it is served and precached by the service worker, exactly like the existing wireframe docs. Consistent with the current convention. Worth a deliberate decision later on whether these review artifacts should be excluded from the production build.

What “done” looks like

acceptance

Checkable outcomes, tied back to the three stated requirements.

  1. Cars and trucks follow roadways. Every position event for a car or truck target lies within a small tolerance of a transportation LineString, and tracks turn at junctions rather than cutting corners. Trucks visibly prefer major classes.
  2. Boats sit in navigable water. No boat position event falls on land. Vessels either follow a real class=ferry route or a coherent lane that rounds headlands instead of crossing them.
  3. Planes fly recognisable patterns. Tracks begin and end at real aerodromes, aligned to actual runway headings; altitude shows a climb, a cruise plateau and a descent; loiter targets hold a racetrack or orbit; and return-to-base targets land where they departed.
  4. Region typing holds. Selecting only maritime regions never produces a road vehicle in water — it relocates or degrades, and says which.
  5. Local-first holds. No new service in docker-compose.yml. Docker reaches only tiles.adversary. Dev may reach OpenFreeMap, controlled by one env var.
  6. Budget holds. First contacts are visible in under about 2 seconds at 100 targets, Cancel works, a 100-target scenario stays in the low thousands of events, generation never blocks the UI thread, and interpolated preview stays responsive after the engine indexing fix.
  7. Degrades cleanly. With the tile source blocked, the demo still loads via the synthetic path and says so.
  8. Reproducible. The same seed produces the same scenario, so the terrain-validity tests are deterministic.
